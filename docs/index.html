01 — Problem

AI writes code fast. Shipping it still needs requirements, review, tests, security and a release decision.

A coding assistant can produce a feature in a minute. A team still has to know what was asked, check that the design fits, test it, scan it, deploy it and decide it is ready. It also has to know what the AI costs and whether it is helping. This project builds that loop for one small service and measures it.

The service is a network device inventory API in Go (routers, switches, OLTs): create, list, get, delete. It is deliberately small, so every agent change can be read in full. Three real GitHub issues went through the pipeline: set a device's status, filter the list by site and role, and validate management IP addresses.

02 — How it works

Models where judgment is needed, plain tools where the answer is yes or no.

  1. Analyst turns the issue into testable requirements

    Cheapest model. Its answer is checked by code (a real summary, at least one requirement, two acceptance criteria) and redone one model up if it fails.

  2. Architect approves the scope and names the files

    Strongest model, from a map of the code (declarations only). It can reject the issue. Its file list is the only set of files the developer may write.

  3. Developer edits, gates answer

    Mid model. It returns small edits, not whole files. gofmt, vet, tests with the race detector and golangci-lint run on every attempt; only the failing lines go back. The last green version is kept, so a bad revision is rolled back.

  4. QA gives the merge verdict from the diff

    Strongest model, judged against the issue and the approved plan. Only findings about planned code go back to the developer; anything else stops for a person.

  5. Docs writes the PR and the changelog, then CI decides

    Cheapest model with the same check-and-escalate rule. The PR must then pass CI, including a deterministic release readiness gate (every job green, service coverage at least 80%, tests and changelog with every service change, the PR links its issue).

03 — Token engineering

Spend the strong model on decisions. Send each role only what it needs.

Model routing

Opus for the scope decision and the merge verdict, Sonnet for code, Haiku for requirements and docs. Escalation happens only on evidence: a failed check or a failed gate.

Context packing

A repo map of declarations is 1,116 characters instead of 6,295 for the source (82% smaller). Only the developer sees full files, only those the architect picked. QA sees the diff.

Structured output

Every role answers in a strict JSON schema: no prose to pay for, no free text to parse. Validators check what the schema cannot: an empty answer is still schema-valid.

Edits, not files

The developer sends find-and-replace edits that must match exactly once. On issue #1, run output fell from 13,320 tokens (whole files) to 8,565.

Compact feedback

A failed gate sends back only the failing check and its last 40 lines. Retries continue the same conversation, so the prefix is read from cache.

Caching, measured

A probe showed the output schema is part of the cached prefix, so roles never share a cache. Caching is now placed only where a prompt is re-sent. At this repo size it saved little: 3.6% of prompt tokens were cache reads.

05 — What broke

Twelve failures, each with the change it caused.

Cheap models return empty answers

Haiku twice returned schema-valid but empty output: requirements reading "placeholder", and a PR with no title or changelog. The release gate blocked that PR. Every cheap step now has a validator and one retry a model up.

CI checked more than the harness

An agent PR passed the local gates and QA, then failed CI lint. The same linter now runs inside the developer's loop.

I broke main

I committed an unformatted file the developer may not touch, and three attempts failed for $0.19. The harness now runs the gates on the base before any model call.

A revision destroyed a green version

QA asked for work the issue never mentioned; the revision broke the tests and nothing rolled back. Now the last green version is kept, and QA judges against the issue and the architect's plan.

07 — Run it

Everything runs from one Go binary.

cp .env.example .env            # ANTHROPIC_API_KEY=...
go build -o sdlc ./cmd/sdlc
./sdlc map                      # the repo map the agents see
./sdlc run -issue 1 -pr         # issue → requirements → plan → code ⇄ gates → QA → docs → PR
./sdlc run -issue 1 -route opus # the routing comparison: every role on Opus
./sdlc naive -issue 1           # baseline: one Opus call with the whole repo
./sdlc redoc -issue 1           # redo only the docs step on an open PR
go run ./cmd/analyst-eval       # which model should write requirements
go run ./cmd/metrics            # ledger + GitHub → results/metrics.json
Source on GitHubAgent pull requests

Limits: three small issues on a 6 KB service, so the routing saving is one comparison, not a benchmark. The single-call baseline was cheaper on this repo; the pipeline pays for requirements, a scope decision, review, docs and guardrails. Total spend for every run on this page, failures and experiments included: $2.13.
